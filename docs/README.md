# 文件

> 狀態：草稿

本資料夾是開發用的**現行文件**：永遠描述系統現在的樣子（或確定要做成的樣子）。

| 入口 | 給誰 | 放什麼 |
|---|---|---|
| [README](../README.md) | 面試官 | 介紹、截圖、功能、技術與選擇理由、之後規劃 |
| [CLAUDE.md](../CLAUDE.md) | AI | 文件表、開發流程、每次都要遵守的工作規則 |
| `docs/` | 開發 | 所有規則與理由 |

## 1. 文件地圖

```
docs/
├── README.md          ← 本文件：文件地圖、以誰為準、寫作規則
├── security.md        ← 跨功能的安全規則
├── data-model.md      ← 資料表、單位、不變條件
├── conventions.md     ← 前後端開發規範
├── devops/            ← 各環境怎麼跑、怎麼操作
│   ├── README.md      ← 環境索引
│   ├── setup-local.md ← 本機：架構、啟動、常用操作
│   ├── setup-dev.md   ← dev（EC2）：架構、部署、常用操作
│   └── setup-mac.md   ← 新手教學：在 Mac 上安裝工具、建立專案
└── specs/             ← 功能規格：README 是功能清單與規則，每個功能一個資料夾
```

## 2. 以誰為準

| 內容 | 以誰為準 |
|---|---|
| 系統行為、驗收條件 | spec 的 REQ、AC；AC 就是測試案例 |
| 資料表 | `data-model.md` 與 Flyway migration 要一致。設計時先在 `data-model.md` 畫，實作後兩邊在同一個 commit 對齊；發現不一致就當成錯誤，先確認哪邊對再修 |
| API 的參數與回應 | springdoc 由程式產生的 Swagger UI；spec 只列用到哪些端點 |
| 畫面的元件與配色 | `/design-system` 頁 |
| 設計決定的理由 | 該主題所在的文件，寫在規則旁邊 |

## 3. 寫作規則

- 一個主題只寫在一個地方，其他文件放連結，不重寫一次。
- 例外：CLAUDE.md 每次對話都會自動載入，AI 絕不能違反的規則（病患資料虛構、不寫實際的密碼）在 CLAUDE.md 也寫一次，內容以 `security.md` 為準。
- 確定要寫、但還沒寫的主題（例如測試）保留標題，當作待辦；不確定要不要的主題不先開標題。
- 檔案太長（約 300 行以上）再拆。
- 每份文件開頭標示狀態：`草稿`、`定案`。不寫日期，修改時間看 git 紀錄。
- 只描述現況，不寫歷史（「原本……後來改成……」）；改變的理由寫在 commit 訊息。
- 程式碼本身就是實作的依據，文件不重寫程式細節。
